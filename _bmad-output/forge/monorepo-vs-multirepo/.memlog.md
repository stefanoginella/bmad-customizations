- (note) Greenfield: project folder empty except BMad scaffolding. Stack: WP marketing (www), Laravel portal (portal), Umami (data), WP connector plugin on client sites. Local: DDEV. Server: Netcup VPS + RunCloud. Plugin auto-updated as part of the care service.
- (crack) Umami is off-the-shelf software, not Stefano's code — putting it in a monorepo may version nothing; weakest of the 4 components
- (assumption) Assumed solo developer, no contractors needing scoped repo access yet — unverified
- (kill) Umami is OUT of the repo decision: pure deployment, zero custom code. At most an infra-notes/env-example folder somewhere, not a codebase
- (note) Access-boundary con is dead: hiring unlikely (Stefano is a dev); a future hire would work on the portal AND likely need the site repo too — so monorepo hides nothing that must stay hidden
- (direction) Decision narrowed to 3 components: WP marketing site, Laravel portal, WP connector plugin
- (lock) Visual identity = a real design-system package in code: one token source (fonts, colors, typography, spacing, motion, buttons, links) that BUILDS to theme.json (+stylesheet) for WP and tailwind config (+stylesheet) for Laravel. Two consumers of one built artifact
- (decision) Pro-monorepo argument #1 survives: a token pipeline with 2 build targets is genuinely painful across separate repos (private package publishing or copy-drift) and trivial in one repo
- (lock) Plugin-portal bond is tight and two-directional: plugin registers REST endpoints portal calls with site key; plugin phones home; portal serves plugin update zips; integration testing = portal + fake client site side by side in DDEV. Pro-monorepo argument #2 survives
- (decision) No license system. Offboarding = uninstall plugin. An orphaned plugin (no active site in portal) becomes pure no-ops by design
- (crack) Karin's rule (open risk): client sites never update in the same minute, so the portal MUST keep speaking to the previous plugin version. Monorepo makes lockstep API+plugin commits tempting — that ease is the risk. Needs contract versioning + ship-order discipline
- (decision) www in git = custom theme + one custom site plugin only. WP core/plugins live on the server (RunCloud + care service). Locally: DDEV full WP install, gitignore everything except the custom theme/plugin — standard pattern, functional site guaranteed
- (decision) Host = GitHub. Deploys driven by GitHub Actions with path filters per app — NOT raw RunCloud webhooks on the monorepo. Henk's every-push-deploys-everything con is neutralized
- (decision) Connector plugin releases: tag plugin-v*, GitHub Action builds the zip from its folder, portal serves the zip to client sites. Subfolder-tagging con is neutralized
- (decision) www layout: theme/ + plugins/ at apps/www root (versioned); full WP install in apps/www/wordpress/ (gitignored); relative symlinks from wordpress/wp-content into the root folders. DDEV project root = apps/www with docroot: wordpress — required, or symlink targets fall outside the container mount
- (decision) www rollback: deploy to releases/<sha> on server + symlink flip in wp-content = instant one-command rollback; fallback = re-run deploy workflow at previous ref. Code only — DB/content rollback stays the job of backups
- (decision) DB+uploads sync: custom DDEV provider (.ddev/providers/prod.yaml) with db/files pull AND push commands over SSH+rsync to RunCloud VPS. Discipline: pull routinely, push only pre-launch — prod DB is source of truth for content
- (lock) AMENDED Karin's rule: portal supports current + previous plugin MINOR version. Patch releases (x.y.Z) never touch the contract — always compatible, so multiple hotfixes can ship in any order. Contract changes require a minor/major bump; plugin ships first
