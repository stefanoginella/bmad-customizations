WOptimize: Monorepo vs Separate Repositories

Session of 2026-08-24 · forged with Stefano

The idea: one repository for the whole WOptimize stack — WordPress marketing site (www), Laravel customer portal (portal), Umami analytics (data), and the connector plugin installed on client sites.

Verdict: the idea survived — one GitHub monorepo, minus Umami. Both pro arguments held under attack. Every con died once tested against the real toolchain (DDEV, RunCloud, GitHub Actions). Umami was expelled: it is deployed software, not a codebase.

Locked decisions

  • Design system is code: one token source builds theme.json + stylesheet for WP and a Tailwind preset + stylesheet for Laravel. One commit updates both apps. Across separate repos this needs private-package publishing or copy-drift. This was pro #1 — it survived.
  • Plugin ↔ portal is a tight, two-directional bond: plugin REST endpoints + phone-home; the portal serves the plugin update zips. Integration testing runs locally: portal + throwaway client site, side by side in DDEV. Pro #2 — it survived.
  • No license system. Offboarding = uninstall; an orphaned plugin becomes pure no-ops.
  • apps/www versions only the custom theme + one site plugin. Full WP install gitignored in wordpress/; relative symlinks from wp-content/. DDEV project root = apps/www, docroot: wordpress — mandatory, or symlinks break in the container.
  • Deploys via GitHub Actions with per-app path filters — no raw RunCloud webhooks on the monorepo.
  • www deploys to releases/<sha>/ + symlink flip → instant one-command rollback (code only; content rolls back via backups).
  • Connector releases: tag plugin-v* → Action builds the zip → portal serves it to client sites.
  • Content sync: custom DDEV provider (.ddev/providers/prod.yaml, SSH + rsync) — ddev pull routinely, ddev push only pre-launch.
woptimize/
├─ apps/
│  ├─ www/          # DDEV root · docroot: wordpress · git: theme + site plugin only
│  ├─ portal/       # Laravel + DDEV
│  └─ playground/   # throwaway WP “client site” for integration tests
├─ packages/
│  ├─ design-tokens/  # source of truth → theme.json + Tailwind preset + CSS
│  └─ connector/      # the plugin installed on client sites
├─ infra/umami/     # docker-compose + .env.example — notes, not code
└─ .github/workflows/  # path-filtered: deploy-www · deploy-portal · release-connector

Killed under scrutiny

  • Umami as a repo component — pure deployment, zero custom code; there is nothing to version.
  • Separate repositories — every claimed advantage died: access boundaries (any future hire needs portal and site), deploy simplicity (path-filtered Actions solve it), release tagging (plugin-v* tags solve it).
  • License server for the connector — uninstall-on-offboarding + no-op fallback is simpler and enough.

Weak points that survived — hold these rules

  • Karin's rule (amended): client sites never update in the same minute. The portal supports the current + previous plugin minor version. Patch releases (x.y.Z) never change the contract — always compatible, so multiple hotfixes can ship in any order. Contract changes require a minor (or major) bump; the plugin ships first, the portal after. The monorepo makes lockstep commits tempting — that ease is the trap.
  • Tomas's rule: tokens and base styles only, until both apps beg for the same component. The design system must not outgrow the product — envelope, not truck.
  • ddev push is a loaded gun: on a live site it overwrites production content. After launch, content flows one way: production → local.
